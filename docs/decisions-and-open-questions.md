## CORE-006 implementation decisions

- Platform grants are separate from organization roles; each platform service checks current active user and grant. They never bypass tenant API authorization.
- Operator bootstrap locks a permanent singleton and checks all grant history. It records an operator action with no fabricated authenticated actor. Revocation does not enable reruns; recovery is a separate unresolved process.
- Company onboarding requires an existing active credentialed owner and writes the organization, explicit owner role, membership, assignments, entitlements, and audits atomically. Existing slugs remain reserved.
- Entitlement catalog: booking, pos, unified_inbox, chatbot. Only booking can be enabled; default is none. Product access does not grant user permissions. Disable preserves data and takes effect on subsequent guarded operations. Already-running Booking transactions require a future policy.
- No new dependency, infrastructure, domain verification, email delivery, or Booking endpoint is introduced. See [CORE-006 design and walkthrough](core-006-platform.md).

## CORE-007 contract decisions

Two explicit Booking inventory permissions are added without automatic owner grants. A platform-authorized, audited operation provisions a marked Booking inventory administrator role for an existing organization role manager. Current service digest plus optional previous digest support rotation; missing current configuration disables the endpoint. Internal requests require both service and Core session headers, current tenant permission, and entitlement. No decision caching or direct Core database access by Booking is permitted. Direct private HTTPS is required outside explicit loopback development/test use. See the [versioned contract](booking-authorization-contract.md); Booking client and gateway implementation remain pending.
