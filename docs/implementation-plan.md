# Implementation plan

CORE-002 is implemented and locally verified; its remote CI run is pending the user's manual push. See [verification evidence](core-002-verification.md). All later checkpoints remain proposed and unstarted. Implement one assigned checkpoint at a time, then stop for review. Each report must identify changed files, checks actually run, failures, and remaining decisions.

The two-week target is a planning constraint, not a completion guarantee. Start with foundation and Core, then Booking and frontend flows, with recovery and release verification before delivery. Re-estimate after each checkpoint. Provider investigation and delivery decisions should start early because external lead times may exceed two weeks.

## Sequencing and delivery dependencies

CORE-002 precedes schema and application work. CORE-003 through CORE-005 establish access boundaries before exposed client Booking flows. Booking transaction tests precede frontend acceptance. Provider research and offline policy decisions can proceed early as separately assigned checkpoints; do not imply that third-party approvals can be completed on demand.

Authentication choices, accommodation rules, domain/DNS control, outbound transactional messaging, provider contracts and approval, deployment access, backup storage, and operational budget may affect delivery. Remote GitHub status and permissions must be confirmed before the user sets up or pushes CI. No remote changes are authorized by this plan.

Stop after CORE-002. The proposed next implementation checkpoint is CORE-003, only when separately assigned. Authentication, initial platform operator bootstrap, and organization/membership isolation decisions must be resolved before its schema and access implementation; see the decision register. No domain work has started.
