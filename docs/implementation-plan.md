## Sequencing and delivery dependencies

CORE-002 precedes schema and application work. CORE-003 supplies persistence safeguards; CORE-004 authentication, CORE-005 permissions, and the proposed domain checkpoint must establish access boundaries before exposed client Booking flows. Booking transaction tests precede frontend acceptance. Provider research and offline policy decisions can proceed early as separately assigned checkpoints; do not imply that third-party approvals can be completed on demand.

Authentication choices, accommodation rules, domain/DNS control, outbound transactional messaging, provider contracts and approval, deployment access, backup storage, and operational budget may affect delivery. CORE-002 CI success is user-confirmed. Repository visibility remains the user's responsibility and is not an implementation blocker. No remote changes are authorized by this plan.

Stop after the assigned CORE-AUTH-003 checkpoint. Booking domain work, domains, frontend, recovery, invitations, MFA, and deployment require separately assigned checkpoints. Local passwords and opaque server-side sessions are implemented; initial operator bootstrap is implemented with permanent history and a serialized one-time grant; subsequent administrator recovery remains unresolved; organization APIs validate explicit organization IDs against current membership, operation capability, and grant authority. Domain-based context remains future work.
